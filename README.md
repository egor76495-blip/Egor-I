
1. Один процесс в двух местах: namespaces и реальное место жительства

Нет, одинаковый PID не означает, что процесс «сидит в двух местах одновременно» — процесс на самом деле живет исключительно на хосте, управляемый ядром Linux.
Контейнеров как изолированных физических сущностей или виртуальных машин в Linux не существует. Контейнер — это обычный изолированный процесс на хосте.
• Где процесс живет «на самом деле»: Процесс выполняется на процессоре хоста и управляется единым ядром операционной системы хоста. Для ядра этот процесс имеет единственный глобальный идентификатор — PID 48231.
• Как получается PID 1: Это результат работы технологии PID namespace (пространства имён процессов). Когда Docker запускает контейнер, он создает для него новое дерево процессов. Внутри этого изолированного «микромира» самый первый запущенный процесс получает виртуальный PID 1.
• Связь с systemd: Так как Docker-контейнер на хосте оформлен в виде systemd-сервиса web-42.service, systemd просто отслеживает этот процесс на уровне хоста. Поэтому в systemctl status отображается его реальный хостовый Main PID: 48231.

2. Запрет CAP_SYS_TIME и общее ядро

Если бы контейнер изменил системное время, часы перевелись бы на всей физической машине и во всех остальных контейнерах сразу, так как у них у всех одно общее ядро.
• Причина изоляции: Контейнеры изолируют ресурсы, но не изолируют ядро (kernel). Системное время (System Time) — это глобальное свойство ядра Linux. В отличие от сетевых интерфейсов или дисков, ядро исторически не умеет «виртуализировать» время индивидуально для каждого пространства имён.
• Связь с разделом 2 (Ядро): Сколько бы виртуальных ядер (vCPU) ни было выделено контейнерам, все они обращаются к одним и тем же часам реального времени (RTC) через единое ядро хоста.
• Что бы случилось: Если бы пользователю root внутри контейнера оставили capability CAP_SYS_TIME, его команда date -s изменила бы время на самом хосте. Как результат: во всех соседних контейнерах сломались бы логи, упали TLS/HTTPS-соединения из-за невалидных сертификатов и нарушилась бы работа баз данных. Поэтому CAP_SYS_TIME всегда жестко вырезается из контейнеров по умолчанию.

3. Сеть в самодельном контейнере без флага --net

Ваш самодельный контейнер будет видеть хостовую сеть и сможет увидеть Nginx на 0.0.0.0:80, запущенный на хосте.
• Какую сеть он видит: Поскольку при вызове unshare не был указан флаг --net, процесс не получил изолированный Network Namespace. Он остался в дефолтном сетевом пространстве имён хоста.
• Видимость Nginx: Да, выполнив внутри этого контейнера команду ss -tlnp, вы увидите точно такой же список открытых портов, как и на хосте, включая хостовый Nginx на 80 порту. Более того, ваш контейнер сможет занять любой свободный порт хоста или перехватить чужой трафик.
• Отличие от web-42 (Docker): Docker для контейнера web-42 принудительно создаёт собственный Network Namespace. Внутри него создается виртуальный сетевой интерфейс (eth0), который через виртуальный мост (docker0) изолирован от сетевых интерфейсов хоста. web-42 видит только свои изолированные loopback (127.0.0.1) и выданный приватный IP-адрес.

4. Общая нить лекции: единый «знаменатель» технологий

Утверждение, что Docker, systemd и Kubernetes — это совершенно разные технологии, неточно, потому что на самом нижнем уровне они являются лишь обертками и инструментами автоматизации над одними итыми же механизмами ядра Linux: Namespaces и Cgroups.
Все три технологии используют один и тот же фундамент для изоляции и ограничения ресурсов, но на разных уровнях абстракции. Общим знаменателем здесь является само ядро Linux.
Каждая из этих технологий по-своему использует базовые механизмы ядра:
• Пространства имён (Namespaces) отвечают за изоляцию и определяют, что процесс может видеть (свои PID, свою сеть, свои точки монтирования). Systemd использует их для ограничения доступа к файловой системе хоста (например, через ProtectHome или PrivateTmp). Docker создает полный стандартный набор пространств имён для каждого контейнера. Kubernetes делает шаг дальше и объединяет несколько контейнеров в один Network Namespace внутри Пода, чтобы они могли делить один IP-адрес.
• Контрольные группы (Cgroups) отвечают за ограничение ресурсов и определяют, сколько процесс может потребить (лимиты по CPU, RAM, IO). Systemd распределяет службы по слайсам и ограничивает их с помощью директив вроде MemoryMax и CPUQuota. Docker транслирует свои флаги запуска (например, -m 512m) в настройки этих же cgroups. Kubernetes берет параметры resources.limits из манифеста подов и передает их на Linux-ноды, где они превращаются в те же самые ограничения cgroups.
